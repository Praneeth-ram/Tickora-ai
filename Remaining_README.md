## Project Goal

Complete Tickora AI as an AI-powered HR chatbot that can interpret employee questions, maintain relevant conversational context, enforce access permissions, retrieve accurate information from PostgreSQL, and return grounded responses.

The roadmap focuses on four areas:

1. Reliable question interpretation and conversation handling.
2. Maintainable backend and database engineering.
3. Security, automated testing, and measurable LLM quality.
4. Production deployment, observability, and operational readiness.

---

# Phase 1 — Make the Chatbot Reliable

**Priority: Highest**

The objective of this phase is to ensure that the chatbot consistently converts user questions into valid, authorized, and correctly executed database operations.

| # | Concept | Implementation objective | Status |
|---|---|---|---|
| 1 | Query-plan validation | Validate every structured JSON operation generated by the LLM, including entity, operation, filters, and required fields. | [ ] |
| 2 | Query-plan correction | Normalize or correct invalid or incomplete plans before execution. Reject plans that cannot be safely corrected. | [ ] |
| 3 | Context management | Handle employee, entity, date, and operation changes in follow-up questions without carrying over irrelevant filters. | [ ] |
| 4 | Conversation persistence | Store conversation sessions and messages durably, with ownership and access isolation. | [ ] |
| 5 | Context-window management | Control the amount of conversation history sent to the model and prevent unnecessary token growth. | [ ] |
| 6 | Ambiguity detection | Ask a clarification question when the employee, date, entity, or requested operation cannot be determined reliably. | [ ] |
| 7 | Response grounding | Generate factual answers from validated database results rather than unsupported model assumptions. | [ ] |
| 8 | Fallback handling | Handle invalid model output, empty database results, inference failures, and timeouts gracefully. | [ ] |

### Phase 1 — Completion criteria

- [ ] Invalid query plans cannot reach database execution.
- [ ] Follow-up questions retain only relevant context.
- [ ] Changing employee or entity updates the appropriate context fields.
- [ ] Ambiguous questions trigger clarification instead of guessed execution.
- [ ] Responses accurately reflect database results.
- [ ] Model and database failures produce controlled responses.

# Phase 2 — Strengthen the Backend Architecture

**Priority: High**

The objective of this phase is to improve backend maintainability, database correctness, concurrency safety, and model resource management.

| # | Concept | Implementation objective | Status |
|---|---|---|---|
| 9 | Centralized exception handling | Define consistent exception types and API error responses across services and routes. | [ ] |
| 10 | Transaction management | Use database transactions where multiple related writes must succeed or roll back together. | [ ] |
| 11 | SQL query optimization | Review slow queries, indexes, execution plans, and unnecessary database operations. | [ ] |
| 12 | Database schema validation | Detect differences between the actual PostgreSQL schema and the application's schema catalog. | [ ] |
| 13 | Concurrency management | Safely handle simultaneous requests, shared model resources, and database access. | [ ] |
| 14 | Cache invalidation | Define expiration and rebuild rules for each cache; distinguish shared model-prefix KV cache from user-specific data. | [ ] |
| 15 | Model lifecycle management | Load the model safely, prevent duplicate loading, manage shutdown, and handle resource cleanup. | [ ] |
| 16 | CPU/GPU inference configuration | Support the intended inference environments with explicit device, precision, quantization, and resource settings. | [ ] |

### Phase 2 — Completion criteria

- [ ] API errors follow a consistent response format.
- [ ] Multi-step database writes use appropriate transaction boundaries.
- [ ] Important database queries have been reviewed with execution plans.
- [ ] Schema catalog mismatches are detected and handled safely.
- [ ] Concurrent requests do not corrupt shared state or model execution.
- [ ] Cache lifecycle and invalidation rules are documented and tested.
- [ ] Model startup and shutdown are predictable.
- [ ] CPU/GPU configurations are tested independently.

# Phase 3 — Security, Testing, and Evaluation

**Priority: Production critical**

The objective of this phase is to protect employee information and establish measurable evidence that the chatbot behaves correctly.

| # | Concept | Implementation objective | Status |
|---|---|---|---|
| 17 | Security testing | Test unauthorized access, role boundaries, employee data isolation, and privilege escalation attempts. | [ ] |
| 18 | Prompt-injection protection | Treat user messages and retrieved content as untrusted; ensure model instructions cannot override backend authorization. | [ ] |
| 19 | Input validation | Validate request schemas, input lengths, identifiers, filters, and supported parameter values. | [ ] |
| 20 | Unit testing | Test individual functions, services, validators, resolvers, and response builders. | [ ] |
| 21 | Integration testing | Test the complete API-to-LLM-to-validation-to-database-to-response workflow. | [ ] |
| 22 | Load testing | Measure throughput, latency, resource usage, and failure rates under concurrent requests. | [ ] |
| 23 | LLM evaluation | Measure intent, entity, operation, filter, identity-resolution, and end-to-end answer accuracy. | [ ] |
| 24 | Regression testing | Ensure new code changes do not break previously working entities, operations, permissions, or follow-up questions. | [ ] |

### Recommended LLM evaluation dimensions

Build a version-controlled evaluation dataset containing representative HR questions and expected structured plans.

| Metric | What it measures |
|---|---|
| Intent accuracy | Whether the request's intent is interpreted correctly. |
| Entity accuracy | Whether the correct HR entity is selected. |
| Operation accuracy | Whether the correct operation is selected, such as list, count, or get. |
| Filter accuracy | Whether dates, statuses, and other filters are extracted correctly. |
| Identity-resolution accuracy | Whether a named employee is resolved to the correct employee record. |
| End-to-end answer correctness | Whether the final answer accurately reflects the expected database result. |
| Authorization rejection rate | Whether unauthorized requests are consistently blocked. |

### Example evaluation cases

| User question | Expected entity | Expected operation |
|---|---|---|
| Show my attendance | Attendance | List |
| How many days was I absent? | Attendance | Count |
| What is my leave balance? | Leave balance | Get |
| Show my payroll for October | Payroll | List |
| Which tasks are assigned to me? | Tasks | List |

### Phase 3 — Completion criteria

- [ ] Employees cannot access records outside their authorization scope.
- [ ] Prompt injection cannot bypass backend permission checks.
- [ ] Unit and integration tests cover critical workflows.
- [ ] Entity-wise and role-wise test cases pass.
- [ ] Regression tests protect existing functionality.
- [ ] LLM evaluation results are recorded and reproducible.
- [ ] Load tests identify acceptable concurrency and resource limits.

## Recommended Implementation Order

Complete the phases sequentially. Within each phase, prioritize correctness and tests over adding more features.

1. **Phase 1:** Query processing, context handling, response grounding, and fallbacks.
2. **Phase 2:** Backend reliability, schema validation, transactions, concurrency, and model lifecycle.
3. **Phase 3:** Security tests, unit/integration tests, regression tests, and LLM evaluation.
4. **Phase 4:** Logging, monitoring, health checks, CI/CD, backups, and deployment security.

Do not mark an item complete simply because a concept has been studied or a code path exists. Verify its behavior with tests and document any known limitations.

---

## Definition of Done

Tickora can be considered ready for a production release only when:

- [ ] The complete request-processing pipeline is validated.
- [ ] Authorization is enforced by the backend for every protected operation.
- [ ] Conversation state is isolated between users and conversations.
- [ ] Responses are grounded in authorized database results.
- [ ] Errors, timeouts, and empty results are handled predictably.
- [ ] Critical workflows have unit, integration, security, and regression tests.
- [ ] LLM quality is measured using a repeatable evaluation dataset.
- [ ] Concurrent requests are tested against the intended deployment capacity.
- [ ] Logging, monitoring, health checks, backups, and recovery procedures are operational.
- [ ] Production configuration and deployment security have been reviewed.

## Important Scope Notes

These technologies are not mandatory for completing the current Tickora architecture. Introduce them only when a concrete requirement justifies the added complexity:

- **RAG:** Useful if Tickora needs to answer questions from HR policies, employee handbooks, or other unstructured documents. It is not required for ordinary structured PostgreSQL queries.
- **Kafka:** Consider for a genuine event-streaming or asynchronous processing requirement at scale.
- **Kubernetes:** Consider when deployment orchestration and scaling requirements justify it.
- **Redis:** Useful for shared session state, distributed rate limiting, or distributed caching; not mandatory for a single-instance deployment.
- **Microservices:** Keep a modular monolith until independent scaling, deployment, or ownership requirements justify splitting services.
- **Multiple agents:** Add only when distinct agent responsibilities provide measurable value.

**Guiding principle:** Prioritize a secure, correct, testable, and observable system over the number of technologies used.
